===== SLIDE 52 =====
Concurrency: Key Takeaways
We need to pay attention to where operations:
• Read data
• Write data
And understand the difference between them.
Concurrent writes cannot be allowed.
• We can only allow one at a time.
Concurrent reads can happen, but:
• They cannot happen during a write.
Critical operations, when 
started, should not be 
interrupted!
In other words, they 
should be atomic

===== SLIDE 53 =====
Concurrency: Atomics and Programming
Consider this Java snippet. Specifically, the third statement.
int a = 10;
int b = 5;
int x = a + b;
How many operations are happening here?
int x = a + b;
(1) Read a from 
memory
(2) Read b from
memory
(3) Add values
of a and b
(4) Write a + b in 
memory (as value x)
A thread managing this task can be 
interrupted by another thread 
running within the same process!

===== SLIDE 54 =====
Concurrency: What could go wrong? 
Lockout
Deadlock
Application Errors
• Software doesn’t do 
what you want it to do
• Programs execute in an 
‘unexpected’ manner.
• Ultimately, the 
‘solution’ is wrong.
• Multiple workers hold a

others. 
• No one will release the

• Ultimately, everything

• Workers access

===== SLIDE 55 =====
Concurrency: So, what now?
Concurrency can lead to some horrific errors when things go wrong.
Those errors can be extremely difficult to debug and reproduce.
You cannot predict when a thread will finish one operations and move on to the 
next.
Fortunately, this isn't a new problem.
• Most programming languages have native support for writing concurrent 
software and controlling threads.
• But as you can imagine, the onus is on the programmer to avoid shooting 
themselves (and others) in the foot.

===== SLIDE 56 =====
Threads in Java: Classes and Interfaces
There are two basic ways of managing Thread objects in Java.
Extending the Thread class.
• Overrides a method called run() which houses the code your threads will 
execute.
• Generally simpler, but less flexible and not very “Object Orientated”.
• Java’s single inheritance means you can’t extend any other class.
Implementing the Runnable interface.
• Forces your class to implement a run() method, but doesn’t necessarily 
violate the stylistic purpose of inheritance
• Any objects implementing runnable can then be used as a Thread object 
parameter, meaning the task can be passed between threads.

===== SLIDE 63 =====
Multithreading: synchronized Methods
The synchronized keyword can be 
used in method signatures. 
If multiple threads can access this object 
in shared memory:
• Only one thread can call a 
synchronized method at a time.
• All other threads must wait for the 
‘current’ thread to finish before they 
can execute any other synchronized 
code.
• In other words, they are
mutually exclusive (mutex)
public class synchronized Counter {
 
private int c = 0;
 
public synchronized void inc() {
 
 
c++;
 
} 
 
public synchronized void dec() { 
 
 
c--;
 
}
 
public synchronized int value() {
 
 
return c;
 
}
}

===== SLIDE 64 =====
Multithreading: synchronized Methods
Synchronised methods are useful, but they:
Can be inefficient 
• The entire method (and all other synchronsized) is locked.
• The ‘critical’ operations might only be a small part of the method
Only ensure mutual exclusion for a shared object, not for arbitrary data!
• We may have an ArrayList we want our thread objects to interact with
• Synchronising access to the list would mean making a new wrapper class to 
control data manipulation through synchronised methods. 
• That can be both inefficient and awkward.

===== SLIDE 68 =====
Multithreading: Summarising Readers and Writer
Read operations need to increment and decrement counters using synchronised 
methods because:
• Write operations might already be happening.
• The counter will need to wait for the write to finish. Once that happens, it can 
increment the counter. 
• Once the counter change starts, no write operations can go ahead and will 
have to wait.
• Counters decrement when finishing a read, preventing write operations until 
notify is called and briefly preventing other read operations from changing the 
counter. 
• If a write operation starts, then it can only enter the synchronized block if no 
other threads are also trying to write or there are ‘active’ reads.
